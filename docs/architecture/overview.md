# Runtime architecture

Revenant is a modular monorepo with one Rust workspace. The running component is `revenant-gateway`, which exposes HTTP health on port 8080 and the versioned game protocol on TCP port 7000.

The gateway and future domain modules remain in one deployable runtime until demonstrated scaling or isolation requirements justify another boundary. Protocol serialization and framing live in the separate `revenant-protocol` library so wire concerns do not spread into future domain systems. `revenant-identity` owns the M2 local account policy and character creation; it has no dependency on wire types. The gateway maps between these boundaries.

M10 adds `revenant-persistence` as the only PostgreSQL boundary. The gateway validates local identity, atomically ensures the initial account/character state, loads character-owned inventory and progression on world join, and records completed activities. SQL and database row mapping do not leak into identity, world, combat, or activity modules. Schema creation is idempotent so the same database survives runtime and container restarts.

M11 adds an append-only replay stream within the same PostgreSQL boundary. The authoritative gateway assigns a session ID at world join and maps domain outcomes to persisted events; neither wire messages nor SQL types enter `revenant-replay`. Each record has an ordered identifier, event type, database timestamp, session and activity identifiers, optional actor identifier, and textual payload. `revenant-replay` owns event vocabulary and deterministic reconstruction, while the `revenant` CLI maps persisted rows into that domain and prints a timeline. This remains one runtime and one database rather than introducing a service boundary.

M12 replaces per-connection gameplay with one in-process shared-session coordinator. Connection threads parse protocol messages and submit typed commands through a channel; the coordinator exclusively owns the actor registry, Lua activity, combat runtime, objectives, encounter stage, persistence, and replay session. Each participant has an outbound channel, and authoritative state changes are broadcast as the existing Protocol V1 server messages. This single-owner event loop avoids shared mutable domain state across socket threads while keeping the gateway as one deployable runtime.

M13 adds a read-only inspection surface over persisted replay data. `revenant-persistence` aggregates session summaries and loads ordered events; the gateway exposes that boundary under `/api/inspector` on its existing HTTP listener. The React/Vite control panel is compiled to static assets and served by an Nginx container that proxies API calls to the gateway. The Inspector never mutates runtime state and does not parse the MessagePack game protocol.

M14 adds `revenant-compatibility` between typed wire parsing and gateway canonical inputs. Handshake negotiation selects either `FrozenV1` or `CurrentV2`; subsequent versioned messages are canonicalized before identity, world, or session logic sees them. V1 and V2 intentionally retain the same field layout in M14, so the adapter establishes the boundary without manufacturing a domain change. The archived V1 client owns a separate schema/framing snapshot and cannot silently follow changes in `revenant-protocol`.

M15 adds an isolated reconstruction harness rather than another production service. `revenant-reconstructed-v1` has no dependency on the current gateway, protocol, compatibility, domain, persistence, or activity crates. Its independent V1 schema was reconstructed only from the author-controlled frozen client, protocol snapshot, and manifest. The canonical smoke first proves normal V1 compatibility, then terminates `revenant-gateway`, starts the harness on the same game address, and proves the unchanged frozen client can authenticate, list its reconstructed character, and enter `relay-hub`. This sharp separation makes the absence of the original backend observable and prevents the experiment from contaminating current runtime architecture.

M16 adds a release boundary without changing the running architecture. A locked build packages the gateway, replay CLI, frozen client, reconstruction harness, Inspector static output, Godot project entry files, Lua activity, and operational documentation. Packaging occurs through a temporary Unix staging tree with normalized timestamps, ownership, ordering, and permissions; identical inputs therefore produce a byte-identical compressed archive across the supported local and CI filesystems. Local artifacts remain ignored, while CI retains the archive and its checksum.

M17 keeps the Godot client thin while making the existing activity manually playable. The client owns input sampling, camera, presentation, aiming selection, and feedback; it sends only `MoveIntent` and `AttackIntent`. The shared-session coordinator confirms admission before the gateway reports a successful world join, validates movement against relay-hub bounds, and owns actor positions, HP, cooldowns, objectives, the door trigger, boss lifecycle, and completion. Server `ActorUpdate`, damage, objective, door, spawn, destroy, and completion messages remain the only source of confirmed HUD/world state. `REVENANT_EXIT_AFTER_FLOW=1` preserves the deterministic automated driver, while normal launches enter the manual event loop after the same handshake and initial AI sequence.

M18 adds `revenant-inventory` as the server-owned item catalog and reward-validation boundary. Lua activity content declares a reward but cannot introduce unknown items or non-positive quantities. On completion, persistence uses an idempotency key to grant each character's reward and record activity history atomically. Current V2 clients receive inventory snapshots and individual loot results; the gateway suppresses those new projections for frozen V1 connections. Replay records each grant so reconstruction and the read-only Inspector expose the authoritative outcome.

M19 adds `revenant-progression` as the owner of experience reward limits and the deterministic level formula. Persistence locks the character progression row and applies experience, derived level, M18 loot, and activity history in one idempotent completion transaction. The mirrored character level keeps selection summaries consistent. V2 receives progression snapshots and grants, while replay and Inspector expose explicit XP totals and level transitions without allowing mutation. V1 projection remains unchanged.

M6 adds a server-side finite-state AI runtime. AI mutates the authoritative `ActorRegistry`; clients observe replicated movement and damage but never execute enemy decisions.
